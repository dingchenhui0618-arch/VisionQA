# VisionQA MVP 团队章程 v0.1

> 文件所有者：产品负责人兼项目经理 Lead  
> 受托人：VisionOS CTO Agent  
> 日期：2026-07-29  
> 状态：`PROPOSED_FOR_CTO_REVIEW`  
> 产品范围：服饰电商 AI 模特商品图、女装上装与连衣裙、天猫/平台促销主图  
> 目标形态：有真实视觉模型参与、全程人工把关、可追溯的受控 MVP  

## 0. 执行摘要

VisionQA 当前已经拥有较完整的可点击 Web 原型、规则和数据契约草案、53 张购买模板及 15 张 Phase 1 商业共识标签，但仍然**没有真实视觉模型运行、候选 AI 图与商品参考图配对 gold set、模型盲测或客户试点**。

因此，本轮 MVP 的成功定义不是“自动发布”，而是：

> 在一批明确授权的服饰电商 AI 模特商品图上，真实运行一个视觉模型，输出可追溯观察、四大 Skill 分、独立硬门禁、商业模板贴合度和修复 Prompt；由人工完成 100% 复核、改判和返工复审；系统能够保留版本、失败、成本、证据及审计记录。

MVP 可以验证工作流和模型是否值得继续投入，但不能宣称提高 CTR/CVR、达到生产准确率或具备自动发布安全性。

## 1. 文档优先级与冲突处理

团队执行时按以下优先级解释产品口径：

1. `PROJECT_STATE.md` 中已确认的用户决定；
2. `AI视觉质量评估系统_策划书_v0.3.md`；
3. `docs/08_核心产品纠偏决定_v0.1.md`；
4. `docs/10_商业价值模板化决策_v0.1.md`；
5. `standards/skill_mapping_v0.2.md`、`contracts/evaluation-result-v0.2.schema.json`；
6. `docs/07_批次审核工作流_PRD_v0.1.md` 中未被新决定覆盖的工作流与审计要求；
7. v0.1/v0.2 旧策划书及 `docs/06_技术验证计划.md` 仅作历史和安全边界参考。

明确覆盖关系：

- 旧 PRD 中“第一阶段不做完整 Web”已经被现有原型实践覆盖，不再作为停止开发的命令；但账号、计费、多租户和规模化部署仍不属于本 MVP。
- 旧技术计划中“`overall_score` 必须为 `null`”已经被 v0.3 纠偏覆盖。MVP 允许输出 0–100 分，但必须标记为 `UNVALIDATED/UNCALIBRATED`，不得用于自动发布。
- 原型中的 `90–100 / 70–89 / 0–69` 仅为产品假设。没有真实盲测前，不得把它包装成生产阈值。

## 2. MVP 必须包含

### 2.1 输入与范围

- 候选 AI 模特图；
- 对应商品参考图；
- SKU 不可变项：颜色、版型、领口、袖型、印花、Logo、关键结构；
- 目标商业模板及版本，首个只支持“天猫 / 平台促销主图”；
- 素材授权、数据集版本、split 和文件哈希；
- 缺少必要资料时形成明确 `scope limitation`，不能让模型猜测。

### 2.2 真实评估链路

- 至少一个真实视觉模型 Provider Adapter；
- 模型只生成结构化观察、证据区域、置信度与建议，不直接决定最终发布；
- 输出通过 evaluation-result v0.2 契约或经正式评审的兼容升级版；
- 确定性门禁规则独立产生 `PASS / REVIEW / REJECT`；
- 技术失败的业务结论必须为 `null`；
- 输入、模型快照、Prompt、规则、模板、成本、延迟和原始响应均可追溯。

### 2.3 产品结果

- 0–100 综合分及真人、摄影、材质、商业四项分；
- Blocker 优先的独立门禁，任何高分不能抵消 Blocker；
- 商业价值绑定具体模板，显示六项相对贴合度与适用性；
- 可核验证据，无法给出精确区域时使用 `FULL_IMAGE`，不得伪造坐标；
- 可复制修复 Prompt，包含锁定项、修复动作、负向约束、策略和关联观察；
- 明确显示“未标定、仅供受控验证”。

### 2.4 人工工作流

- 批次网格、排序、筛选与单图证据详情；
- 100% 人工复核所有系统 `PASS`；
- 人工确认/改判必须记录操作者、时间、原因和证据；
- 原系统结论不可被覆盖；
- 返工图形成新版本，能对照“已解决、仍存在、无法判断、新问题”；
- 没有完成必要人工处置的批次不能标记为完成。

### 2.5 持久化与评测

- 审计必须服务端持久化；浏览器本地存储只可作为演示降级，不算 MVP 验收通过；
- 真实模型运行和失败均写入不可静默覆盖的记录；
- 有 development / validation / blind test 的组级隔离；
- 能计算门禁、评分、证据、Prompt、稳定性、延迟和成本指标；
- 所有失败样本保留，禁止通过删样本、改标签或放宽验收制造通过。

## 3. MVP 明确排除

- 自动发布或与电商平台自动上架；
- “≥90 即可安全发布”的生产承诺；
- CTR/CVR 提升、节省人力比例或商业 ROI 声明；
- 自训练模型、微调、多模型投票和模型路由优化；
- 多行业、多品类、多渠道同时扩张；
- 视频、3D、纯白底商品图和广告创意生成；
- 完整账号体系、复杂 RBAC、多租户、订阅、计费和支付；
- 生产级大规模队列、SLA、高并发和私有化部署；
- 法律、平台合规或品牌一致性的保证；
- 使用 53 张购买模板代替候选图/商品参考图配对 gold set；
- 将模型修复 Prompt 直接执行后视为安全结果；
- 在盲测通过前调整 HIGH 阈值以迎合当前样本分布。

## 4. 团队结构与角色契约

### 4.1 组织原则

- CTO Agent 只负责编排、接口裁决、风险升级和阶段门禁，不直接替代各 Lead 执行。
- 每项产物只有一个唯一写入者；其他 Agent 通过评审意见或任务书提出修改。
- 执行者不能批准自己的交付物。
- 测试评测 Lead 对内部 Gate 有否决权；用户/创意总监保留最终产品、审美与外部 Go/No-Go 权。
- 受并发限制，角色可以分批启动；不能因为未同时运行而合并独立验收权。

### 4.2 CTO / 总控 Agent

**职责**

- 判断角色与依赖、拆解任务、签发任务书；
- 维护跨 Lead 接口、冲突、风险和阶段状态；
- 确保执行者与验收者分离；
- 将产品、审美、隐私、成本和对外声明升级给用户；
- 不亲自修改各专业 Lead 的主交付物。

**输入**

- 本章程、`PROJECT_STATE.md`、各 Lead 任务报告、外部审查意见。

**输出**

- 带唯一 ID 的任务书；
- 集成顺序、责任矩阵、风险和决策升级清单；
- Gate 评审记录及 Go / Revise / No-Go 建议。

**验收标准**

- 每项任务包含 owner、inputs、outputs、acceptance、reviewer、路径白名单和状态；
- 没有同一 Agent 自产自批；
- 所有跨角色接口有版本与唯一责任人；
- 未验证结果没有被写成成功；
- 最终 Go 必须取得用户/创意总监批准。

### 4.3 产品负责人兼项目经理 Lead

**职责**

- 冻结 MVP 用户、场景、范围、工作流和成功定义；
- 管理需求优先级、里程碑、依赖和外部审查点；
- 统一冲突文档口径；
- 定义内部验收与用户外部裁决边界。

**输入**

- 策划书 v0.3、PRD、决策记录、项目状态、评测报告、用户反馈。

**输出**

- MVP 章程、范围清单、里程碑、跨团队依赖、验收矩阵；
- 后续 PRD 修订任务书和外部审查 Brief。

**验收标准**

- 必须项和排除项无冲突；
- 每个功能可追到用户价值和可测试验收；
- 原型、真实能力和未来能力被明确区分；
- 外部审查权未被 Agent 替代；
- 经 CTO 审查、测试 Lead 反向检查、用户确认。

### 4.4 AI / 模型工程 Lead

**职责**

- 建立 Provider-neutral 真实视觉模型 Adapter；
- 设计结构化观察 Prompt、解析、重试和失败状态；
- 保存模型快照、原始响应、延迟和成本；
- 不让模型直接决定门禁，不宣称未测准确率。

**输入**

- 候选图与商品参考图；
- taxonomy、Skill 映射、Prompt 契约、evaluation schema；
- 数据授权与隐私限制；
- 测试 Lead 冻结的 development/validation/test split。

**输出**

- 单模型 Adapter；
- 结构化观察 Prompt 与版本；
- 原始响应引用、解析器、失败状态和运行清单；
- 小样本运行报告、成本与延迟基线。

**验收标准**

- 成功输出通过冻结 Schema；
- `TIMEOUT / PROVIDER_ERROR / INVALID_OUTPUT` 不产生业务决策；
- 每次运行可追到输入哈希、模型、Prompt、配置、延迟和成本；
- 凭证不进入日志；
- 在冻结样本上可复跑，所有失败保留；
- 由平台 Lead 做接口评审、测试 Lead 做独立验收。

### 4.5 视觉标准与 Prompt Lead

**职责**

- 维护四大 Skill、服饰规则码、门禁、严重度与证据定义；
- 完成 0–100 锚点和商业模板六项指标的可标注化；
- 定义修复 Prompt 的锁定项、修复项、策略和安全负向约束；
- 制作 LOW 受控失败变体及单变量记录，但不得把合成变体包装成真实业务数据。

**输入**

- taxonomy、gates、rubric、skill mapping；
- Phase 1 共识标签、53 张授权购买模板；
- 用户审美/业务意见和真实商品不可变项。

**输出**

- 标准包与版本映射；
- HIGH/MEDIUM/LOW、NOT_APPLICABLE、NOT_ASSESSABLE 锚点；
- 6–10 张 LOW 受控变体及变更记录；
- 修复 Prompt 模板、证据要求和禁改项。

**验收标准**

- 每条规则有定义、适用条件、严重度、证据和行动；
- Blocker 不可被分数抵消；
- 至少两位独立评审者能按同一版本使用；
- 受控变体只有一个明确主变量，原始图、变体和授权可追溯；
- Prompt 不修改 SKU 锁定事实；
- 由测试 Lead 验证一致性，审美与商业解释由用户/外部评审裁决。

### 4.6 全栈与数据平台 Lead

**职责**

- 将现有原型升级为真实评估工作台；
- 实现批次、资产版本、运行、人工改判、返工和审计的持久化；
- 接入模型任务状态与失败安全；
- 保证系统结论和人工结论并存，不静默覆盖。

**输入**

- 产品工作流与验收；
- evaluation schema、数据库 schema、模型 Adapter 接口；
- UX 规格、身份信息和数据治理要求。

**输出**

- 服务端数据模型与迁移；
- 批次/评估/改判/返工 API；
- 模型运行状态接入；
- 可部署的受控 MVP 和运维说明。

**验收标准**

- D1 或选定数据库真实绑定；重载、换浏览器后审计仍存在；
- 每次运行和改判追加写入，原始记录不被覆盖；
- 技术失败显示独立异常，不伪装成业务 `REVIEW`；
- 未复核 PASS 不能完成批次；
- 构建、lint、单元/集成测试通过；
- 由测试 Lead 验收，数据安全由治理审查者复核。

### 4.7 UX / 视觉产品 Lead

**职责**

- 维护苹果式克制、证据优先的视觉体系；
- 设计真实数据、加载、失败、范围不足、人工复核和返工对比状态；
- 保证商业模板、四大 Skill、门禁与 Prompt 的信息层级；
- 进行桌面与核心响应式可用性验证。

**输入**

- 已确认的 A 为主、B 为证据详情方向；
- UI v0.3、产品工作流、真实 Schema 与错误状态；
- 用户审美反馈及外部 UX 审查意见。

**输出**

- MVP 页面规格、状态矩阵、组件与视觉 token；
- 关键流程原型或实现评审；
- 可访问性和响应式检查报告。

**验收标准**

- 用户能在不读技术日志的情况下回答“哪张、多少分、为何、怎么改、谁确认”；
- 分数、门禁和未标定提示不相互误导；
- 问题不只靠颜色表达；
- 失败、无数据、不可评估和权限不足状态均有设计；
- 用户/创意总监拥有最终审美批准权，Lead 不自批。

### 4.8 测试与评测 Lead

**职责**

- 冻结数据 split 和盲测协议；
- 建立契约、规则、模型、UI 和端到端回归；
- 计算门禁召回、危险误放、评分一致性、证据可核验率、Prompt 效果、稳定性、成本和延迟；
- 对 Gate 2/3 给出独立 Go / Revise / No-Go。

**输入**

- 冻结标准、Schema、Adapter、应用版本；
- 授权数据、双人标签、裁决结果和运行日志；
- 用户确定的错误成本偏好。

**输出**

- 测试计划、gold/holdout 版本、盲测报告、错误分析和回归套件；
- Gate 证据包和独立发布建议。

**验收标准**

- test 未参与 Prompt、规则或阈值调优；
- 数据按 SKU/生成批次/近似图组隔离；
- 同时报告通过与失败，缺失指标不填造；
- Blocker 被分数抵消次数为 0；
- 技术失败不产生发布结论；
- 没有真实 gold set 时必须给出 No-Go 自动发布结论；
- 该 Lead 可否决内部进入下一 Gate，但不能代替用户做最终商业批准。

### 4.9 数据治理与安全审查角色

该角色可以是阶段性内部 Agent 加外部人工审查，不必在 MVP 早期配置为全职开发 Agent，但在真实素材进入前必须存在。

**职责**

- 审查授权、供应商处理边界、访问、保留、导出、删除和凭证管理；
- 检查日志、原始响应和部署配置是否泄露敏感信息；
- 审查外部模型处理真实客户素材的风险。

**输入**

- 数据授权声明、供应商条款、系统架构、日志样本、存储和删除方案。

**输出**

- 数据处理清单、风险登记、访问/保留/删除规则、进入真实试点的安全意见。

**验收标准**

- 每类素材有 owner、purpose、location、access、retention、deletion；
- 密钥和签名 URL 不入日志；
- 未明确授权的数据不发送第三方；
- 高风险未关闭时可以否决真实客户试点。

## 5. 共享接口与唯一写入者

| 共享对象 | 唯一写入者 | 必须评审者 |
|---|---|---|
| MVP 范围、里程碑 | 产品/项目 Lead | CTO、测试 Lead、用户 |
| taxonomy / rubric / gates / Prompt 标准 | 视觉标准 Lead | 测试 Lead、用户 |
| evaluation schema 与 Adapter 接口 | AI Lead（观察层）+ 平台 Lead（传输/持久化，各自独立文件） | 对方 Lead、测试 Lead |
| 数据集 split 与 gold label | 测试 Lead | 视觉标准 Lead、外部评审 |
| Web 交互规格 | UX Lead | 产品 Lead、用户 |
| 服务端数据与审计 | 平台 Lead | 测试 Lead、安全审查 |
| `PROJECT_STATE.md` | CTO 指定的项目状态维护者 | 各 Lead 提供事实，用户可审查 |
| Go / No-Go 证据包 | 测试 Lead | CTO、用户、外部审查 |

任何跨接口修改都必须升级版本，不允许通过直接改对方文件来“顺手修复”。

## 6. 里程碑与门禁

工期仅是依赖顺序估算，不是对外承诺；真实素材和外部审查等待时间不包含在内。

### M0 · 团队与范围冻结（1 个工作日）

**交付**

- 本章程；
- 角色任务书；
- 文档优先级、路径白名单和共享接口清单。

**内部验收**

- CTO 确认所有任务有 owner 和独立 reviewer；
- 测试 Lead 确认验收项可测。

**外部审查点 ER-0**

- 用户确认 MVP 的场景、必须项、排除项和“不会自动发布”。

### M1 · 标准、契约和数据准备就绪（2–4 个工作日）

**交付**

- 标准版本清单与跨文件差异修复；
- 真实评估输入 manifest；
- 6–10 张 LOW 受控变体及修改记录；
- 真实模型接口契约和失败状态样例；
- 数据治理初审。

**内部 Gate 1**

- 两人可独立使用标准；
- Schema 示例全部有效；
- 数据授权和 split 可追溯。

**外部审查点 ER-1**

- 商业/视觉外部评审确认 LOW 变体确实只破坏目标维度；
- 用户裁决审美或商业分歧。

### M2 · 首个真实模型离线闭环（3–5 个工作日）

**依赖**

- M1；
- 可调用的模型凭证；
- 已授权的开发样本。

**交付**

- 单模型 Adapter；
- 原始响应、结构化观察、规则门禁和版本日志；
- 重复运行、成本、延迟和失败分析。

**内部验收**

- Schema、失败安全、Blocker 不可抵消和可复现检查通过；
- 本阶段不要求模型准确率达标。

**外部审查点 ER-2**

- 外部技术审查者检查“模型观察/规则决策”分离和失败安全。

### M3 · 持久化端到端工作台（3–6 个工作日）

**依赖**

- M2 接口稳定；
- UX 状态矩阵；
- 服务端数据库可用。

**交付**

- 批次上传、真实运行、结果查看、人工改判、返工版本和审计；
- 真实失败/空状态；
- 私有受控部署。

**内部 Gate 3a**

- 自动化测试通过；
- 换浏览器仍能追溯审计；
- 100% PASS 人工复核规则可执行；
- 技术失败不会形成业务通过。

**外部审查点 ER-3**

- 用户完成一次端到端任务；
- 外部 UX 审查角色检查是否能理解证据与修复 Prompt。

### M4 · Gold set 与盲测（素材到位后 5–10 个工作日）

**硬依赖**

- 20–30 组起步的候选 AI 图 + 商品参考图 + SKU 锁定项；
- 两名独立标注者；
- 用户确认危险误放与过度拦截的优先级。

**交付**

- development / validation / test；
- 双人标签、分歧裁决；
- 模型、门禁、评分、证据和稳定性盲测报告。

**内部 Gate 2**

- 测试 Lead 独立给出 Go / Revise / No-Go；
- 未满足阈值时不得改标签或移动 test 样本。

**外部审查点 ER-4**

- 外部评审核对盲测方法和代表性；
- 用户批准是否进入人工辅助试点。

### M5 · 修复 Prompt 返工回归（与 M4 后半并行）

**依赖**

- 可执行返工的图片、锁定项和生成/修图工具；
- 人工确认修复前后版本。

**交付**

- Prompt 采纳、目标问题解决、新问题引入和锁定项违反报告；
- 前后版本证据链。

**内部验收**

- Prompt 不是只看语言质量；
- 至少按“解决/未解决/新问题/违反锁定项”实测；
- 任何违反商品锁定项的 Prompt 判失败。

**外部审查点 ER-5**

- 出图师或设计师判断 Prompt 是否可执行；
- 用户判断商业改进是否成立。

### M6 · 受控人工辅助 MVP 决策

**准入**

- M2、M3 完成；
- M4 与 M5 有真实证据；
- 数据治理问题关闭或明确接受；
- 测试 Lead 未给 No-Go。

**输出**

- 只面向受控用户、所有 PASS 仍人工复核的 MVP；
- 试点监控、回滚、抽检和问题升级方案。

**最终外部 Gate**

- 用户/创意总监拥有最终 Go / Revise / No-Go 权；
- 外部测试/技术/业务审查意见必须进入决策记录；
- 即使进入试点，也不等于批准自动发布。

## 7. 内部验收与外部审查权

| 事项 | 内部团队能做什么 | 外部/用户保留权 |
|---|---|---|
| 构建、Schema、API、回归测试 | 判定通过或失败 | 可要求复核证据 |
| 模型盲测统计 | 测试 Lead 独立计算并否决 | 外部评审核查方法与代表性 |
| 视觉锚点和商业解释 | 提议、统计一致性 | 用户/创意总监最终裁决 |
| 修复 Prompt 可执行性 | 测试结构和锁定项 | 出图师/设计师确认实际可用 |
| 数据授权与第三方处理 | 记录、执行控制 | 数据权利人/安全审查批准 |
| 进入受控 MVP | CTO 给建议 | 用户最终批准 |
| 自动发布 | 内部只能提交未来提案 | 本 MVP 禁止；未来需单独外部批准 |
| 对外准确率、ROI、CTR/CVR 声明 | 内部提供证据 | 用户及相应业务/合规审查批准 |

外部评审意见不直接修改源文件。产品 Lead 负责记录意见，唯一写入者修改，测试 Lead 验证修订是否落实。

## 8. 关键依赖

```text
产品范围冻结
  ├─→ 标准/Prompt 冻结 ─→ 标注协议 ─→ gold set ─→ 盲测
  ├─→ Schema 冻结 ─→ 模型 Adapter ─→ 平台接入 ─→ 端到端工作台
  ├─→ UX 状态矩阵 ───────────────────→ 端到端工作台
  └─→ 数据治理 ─→ 允许发送真实素材 ─→ 模型运行/试点

真实模型 + gold set + 工作台 + Prompt 回归
  └─→ 受控人工辅助 MVP 决策
```

当前最关键的外部依赖不是更多商业模板，而是**候选 AI 模特图与商品参考图的授权配对样本**。

## 9. 风险登记

| 等级 | 风险 | 影响 | 所有者 | 当前缓解 |
|---|---|---|---|---|
| 高 | 没有配对 gold set | 无法判断商品忠实度、门禁召回与自动阈值 | 产品 + 测试 | MVP 保持人工辅助；M4 前不得宣称准确率 |
| 高 | 当前商业锚点只有 MEDIUM | 无法验证 HIGH/LOW 和细粒度排序 | 标准 + 测试 | LOW 做受控变体；HIGH 等外部优质成品 |
| 高 | 真实模型尚未运行 | 原型能力可能与实际输出差距大 | AI Lead | M2 优先单模型离线闭环 |
| 高 | 修复 Prompt 未做返工回归 | 可能“听起来正确”但改坏商品 | 标准 + 测试 | M5 强制锁定项和前后对照 |
| 高 | 证据坐标幻觉 | 人工被虚假精确性误导 | AI + UX | 支持 `FULL_IMAGE`；评测证据可核验率 |
| 高 | 真实素材数据处理边界未冻结 | 供应商、隐私和授权风险 | 数据治理 | 真实客户素材进入前完成审查 |
| 中 | 线上 D1 未绑定 | 审计不能跨浏览器持久化 | 平台 Lead | M3 作为硬验收 |
| 中 | 旧文档口径冲突 | Agent 按不同基线执行 | 产品 Lead | 本章程定义优先级；后续修订 PRD |
| 中 | 商业分被误解为转化预测 | 对外承诺风险 | 产品 + UX | 文案统一为模板贴合度，不声称 CTR/CVR |
| 中 | 单一模型成本/延迟不明 | 试点不可运营 | AI + 平台 | M2 实测 p50/p95、成本和失败率 |
| 中 | 外部评审变成事后背书 | 独立性不足 | CTO + 测试 | 评审者提前看到协议，不参与 test 调优 |
| 中 | 为过 Gate 调阈值或标签 | 评测失真 | 测试 Lead | 冻结 test，保留所有失败，独立否决权 |

## 10. CTO 需向其他 Lead 提出的接口问题

### 给 AI / 模型工程 Lead

1. 首个 Provider Adapter 需要哪些凭证、图像输入限制和结构化输出约束？
2. evaluation-result v0.2 能否直接承载原始观察、模型失败和成本，还是需要 v0.3 向后兼容升级？
3. 证据区域在供应商不支持定位时如何可靠降级为 `FULL_IMAGE`？
4. Prompt 生成是与观察同一次调用，还是独立版本化调用？

### 给全栈与数据平台 Lead

1. D1 绑定和当前 deployment 的实际差距是什么？
2. 批次、资产版本、模型运行、改判、返工和审计是否已有完整迁移，缺哪些表或约束？
3. 长任务采用同步、轮询还是最小队列；如何保证重复提交幂等？
4. 原图、参考图和原始响应存储在哪里，如何删除与追溯？

### 给视觉标准与 Prompt Lead

1. 6–10 张 LOW 受控变体的原图、单变量和预期降分分别是什么？
2. 四大 Skill 的 0–100 锚点是否已足够两人试标？若不足，缺哪些可观察定义？
3. 商品锁定项最小结构如何从 SKU/reference 输入产生？
4. Prompt 的 `LOCAL_EDIT / REGENERATE / MANUAL_REVIEW` 如何被规则触发？

### 给 UX / 视觉产品 Lead

1. 真实运行、排队、失败、不可评估、scope 有限和未标定状态是否都已有界面定义？
2. 如何在不弱化总分价值的同时，防止用户把总分当发布批准？
3. 返工前后证据和标准版本变化如何展示？
4. 外部审查应使用哪三条端到端任务脚本？

### 给测试与评测 Lead

1. 当前 15 张商业锚点能验证哪些字段，明确不能验证哪些字段？
2. M2 无真实 gold set 时，最小可验收项和 No-Go 边界是什么？
3. 20–30 组数据怎样按 SKU、生成批次和近似图分组切分？
4. Gate 2 的数值阈值何时、由谁、基于哪种业务损失冻结？

## 11. 第一批 CTO 任务签发建议

建议 CTO 同时启动三个互不冲突的首批任务：

1. `MVP-AI-001`：AI Lead 只读审查 Schema 与现有 runner，提交真实 Adapter 接口和差距报告，不接触 test；
2. `MVP-STD-001`：视觉标准 Lead 制作 LOW 受控变体方案和修复 Prompt 评测协议；
3. `MVP-PLAT-001`：平台 Lead 审查 D1、审计和异步运行差距，提交实现顺序；

测试 Lead 应在上述方案提交后独立形成 `MVP-QA-001` 验收矩阵；UX Lead 基于真实状态清单形成 `MVP-UX-001`。任何 Lead 在计划审查通过前不得大范围改动共享接口。
