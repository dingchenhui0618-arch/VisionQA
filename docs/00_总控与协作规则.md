# 总控与多 Agent 协作规则 v0.1

## 1. 人与 Agent 的职责

### AI 产品负责人 / 创意总监（人）

拥有最终产品方向和审美裁决权，负责：

- 选择首个目标客户和垂直场景；
- 提供正例、反例及判断理由；
- 裁决无法通过规则消除的审美分歧；
- 批准阶段性 Go / No-Go；
- 决定品牌、商业价值与产品范围。

### 总控 / 项目经理 Agent

负责：

- 拆解任务、检查依赖和分配角色；
- 维护项目状态、风险和决策记录；
- 检查交付物是否满足验收标准；
- 触发跨角色评审与测试门禁；
- 将需要主观或商业判断的问题升级给创意总监。

总控 Agent 不替代创意总监裁决审美，也不替代测试 Agent 宣布评测通过。

### 默认推进原则

- 总控 Agent 在已批准范围内持续推进，不因普通任务切换等待创意总监逐项指示；
- 可逆、低风险且不改变产品方向的决定，由总控 Agent采用合理默认值并记录；
- 多个需要裁决的问题集中成一轮，不零散打扰；
- 只有涉及产品方向、不可逆操作、客户数据、法律风险、对外发布或重大成本时才暂停等待；
- 暂无真实素材时，先完成标准、契约、评测设计和模拟验证，明确标注未验证结论；
- 默认值不等于最终标准，真实数据到位后必须重新标定。

### 产品 Agent

负责用户、场景、PRD、工作流、竞品、需求优先级和验收标准。

### 技术 Agent

负责架构、数据契约、模型适配、版本追踪、API、成本、延迟和最小验证工具。

### 视觉标准 Agent

负责缺陷分类体系、发布门禁、评分 rubric、正反例、严重度和 Skill 文档。

### 测试评测 Agent

负责标注协议、数据集切分、一致性分析、盲测、回归测试和发布门禁。评测未通过时有权否决进入下一阶段。

## 2. 强制交接格式

每个任务必须包含：

```yaml
task_id: 唯一编号
owner: 责任角色
objective: 要解决的问题
inputs: 输入文件和版本
outputs: 预期交付物
acceptance: 可验证的验收条件
reviewer: 评审角色
status: backlog | active | review | blocked | done
```

任务完成时必须给出：

- 产物路径；
- 使用的输入版本；
- 已通过和未通过的验收项；
- 已知风险与假设；
- 是否需要创意总监决策。

### 2.1 执行任务书附加要求

当任务进入可执行阶段时，任务书还必须明确：

- 为什么做，以及发生冲突时的优先级；
- 允许修改的路径白名单；
- 不允许修改的验收标准、测试和数据集；
- 任务开始前需要核对的现状与基线；
- 可复跑的验收方式和实际输出证据；
- `PROGRESS.md` 断点续跑记录；
- `BLOCKED.md` 待裁决事项；
- 连续三次无法通过同一验收时停止该路径并报告；
- 结果差于基线时不得包装成成功。

执行 Agent 不得通过删除样本、放宽阈值、改标签、跳过测试或修改验收脚本来制造“通过”结果。

## 3. 版本追踪要求

每次模型评估至少记录：

```text
image_id
scenario_id
model_provider
model_version
prompt_version
skill_version
rubric_version
dataset_version
raw_response
parsed_result
latency
cost
timestamp
```

## 4. 阶段门禁

### Gate 0：场景冻结

- 明确一种客户；
- 明确一种素材；
- 明确一个发布渠道；
- 明确“通过、复核、拒绝”的业务含义。

### Gate 1：标准可标注

- 每项标准有定义、适用条件、严重度和评分锚点；
- 至少两名标注者能独立使用；
- 分歧有记录和裁决机制。

### Gate 2：基线评测

- 有独立盲测集；
- 记录误放率、误杀率和稳定性；
- 严重错误不能被其他高分抵消；
- 结果可复现。

### Gate 3：MVP 产品化

- 基线达到预设 Go 阈值；
- 报告建议可被用户理解并执行；
- 端到端流程有日志、失败处理和版本追踪。

## 5. 当前禁止事项

- 未冻结首个场景前扩展到多个行业；
- 未完成评测标准前开发完整网站；
- 用单一总分替代严重问题门禁；
- 测试集参与 Prompt 调优；
- 只展示成功案例，不记录失败案例；
- Agent 自己制定标准后再自己宣布标准有效。

## 6. 外部 Leader Skill 的采用范围

参考 `KKKKhazix/khazix-skills/leader`，本项目采用：

- 任务书与执行工作的分离；
- 一轮只询问少量真正影响方向的问题；
- 路径白名单与任务边界；
- 可复跑验收和反向验证；
- `PROGRESS.md` / `BLOCKED.md` 断点机制；
- 执行者不能自己批准自己的交付物；
- 多 Agent 任务必须声明共享上下文、接口和唯一写入者。

暂不采用：

- 把单份 `/goal` 任务书作为整个项目唯一事实来源；
- 强制所有任务都限制为一次性、4000 字符以内；
- 将探索型产品工作完全转成机器判定；
- 在项目尚未冻结场景时进行高度自治的长周期执行。

原因：VisionQA 当前仍包含产品判断、视觉标准裁决和真实业务验证，必须允许阶段性人工决策。该外部 Skill 更适合作为“执行任务书生成器”，而不是替代项目总控。
