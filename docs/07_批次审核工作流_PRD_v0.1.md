## 1. 文档目标

本文定义未来 MVP 的批次审核工作流及验收标准，供产品、设计、技术和测试评审使用。

第一阶段仍以离线评测为主，**不开发完整 Web 产品**。本 PRD 不构成开发启动批准；只有离线基线通过 Gate 2 后，才进入界面与端到端产品化。

当前没有真实客户素材、品牌规则、线上返工记录或经过标定的阈值。凡涉及批次数量、自动判定置信度、Major/Minor 聚集、处理时限、抽检比例和业务效果的内容，均不得解释为已验证结论。

## 2. 产品目标与非目标

### 2.1 产品目标

帮助服饰电商 AI 内容团队：

1. 以批次提交 AI 模特商品图及必要参考材料；
2. 将候选图分流为 `PASS`、`REVIEW`、`REJECT`；
3. 查看每个结论对应的门禁、证据区域和修改动作；
4. 由人工完成复核、改判和最终发布确认；
5. 对返工后的新版本重新审核；
6. 保留完整、可追溯、不可静默覆盖的审计记录。

### 2.2 验证期强制规则

- 验证期所有 `PASS` 必须经过 **100% 人工复核**；
- 系统不得自动发布或把 `PASS` 表述为最终发布批准；
- 缺少商品参考材料时，不得声称商品忠实度已验证；
- 合规能力仅为视觉风险提示，不替代法务或平台政策判断；
- 硬门禁优先，软评分不得抵消 Blocker；
- 技术失败的业务决策必须为 `null`，不得伪装为 `REVIEW` 或其他业务结论。

### 2.3 第一阶段不做

- 完整 Web 前端、账号、订阅和支付；
- 自动发布到电商平台；
- 视频、3D、纯商品白底图和广告概念图；
- 自训练模型；
- 未经标定的 0–100 综合分；
- 将模型生成的 Prompt 直接当作通用修复方案；
- 用模拟样本宣称真实业务准确率。

## 3. 用户角色与权限

### 3.1 批次创建者

典型用户：AI 出图师、设计师、审核专员。

权限：

- 创建批次；
- 上传候选图和参考材料；
- 补充 SKU、渠道和品牌信息；
- 查看系统结果；
- 提交返工版本。

默认不能最终批准发布，除非同时拥有“发布复核人”权限。

### 3.2 发布复核人

典型用户：审核专员、视觉负责人、商品或品牌负责人。

权限：

- 查看全部候选图、证据和门禁结果；
- 确认或改判系统结论；
- 填写改判原因；
- 确认返工是否完成；
- 在验证期对每个 `PASS` 完成人工复核；
- 给出最终“允许进入发布流程”或“退回”的人工结论。

### 3.3 标准管理员

典型用户：视觉标准负责人。

权限：

- 查看使用中的 taxonomy、gates 和 rubric 版本；
- 发布经过评审的新标准版本；
- 查看人工改判聚合，但不能修改历史运行所绑定的版本。

标准管理员不得通过后台直接覆盖某次审核的原始模型观察或历史人工结论。

### 3.4 审计查看者

典型用户：项目负责人、测试评测人员。

权限：

- 只读查看批次、运行、改判、返工和版本记录；
- 导出用于评测的审计数据；
- 不得修改业务结论。

### 3.5 权限假设

> **未验证假设 R-01：** 真实团队是否需要四类独立角色尚未访谈。本 PRD 先定义职责，不锁定具体 RBAC 颗粒度；MVP 可允许一人拥有多个角色。

## 4. 核心对象与状态

### 4.1 批次 Batch

建议字段：

```text
batch_id
batch_name
scenario
product_category
channel
placement
creator_id
reviewer_ids
status
created_at
submitted_at
completed_at
```

批次状态：

```text
DRAFT
→ VALIDATING
→ READY
→ EVALUATING
→ AWAITING_HUMAN_REVIEW
→ COMPLETED
```

异常状态：

```text
INPUT_REQUIRED
EVALUATION_PARTIAL
EVALUATION_FAILED
CANCELLED
```

### 4.2 候选素材 Asset

一个候选素材代表待审核图片的一个版本。返工后应创建新版本，不覆盖旧图。

建议字段：

```text
asset_id
asset_version
parent_asset_id
asset_sha256
sku_id
reference_asset_ids
submission_context
evaluation_run_id
system_decision
human_decision
final_disposition
```

### 4.3 审核运行 Evaluation Run

每次运行必须绑定：

- 代码版本；
- 数据集或输入清单版本；
- taxonomy、gates、Prompt、适配器版本；
- 供应方返回的模型快照；
- 配置哈希；
- 原始响应引用；
- 延迟、尝试次数和成本状态。

相同图片再次运行必须创建新 `run_id`，不得静默替换旧结果。

### 4.4 决策层级

系统决策：

```text
PASS | REVIEW | REJECT | null
```

人工决策：

```text
CONFIRM_PASS
OVERRIDE_TO_REVIEW
OVERRIDE_TO_REJECT
CONFIRM_REVIEW
OVERRIDE_TO_PASS
CONFIRM_REJECT
RETURN_FOR_RESUBMISSION
```

最终处置：

```text
APPROVED_FOR_PUBLISHING_FLOW
REQUIRES_ACTION
REJECTED
SUPERSEDED_BY_NEW_VERSION
```

系统结论和人工结论必须分别保存。

## 5. 批次创建

### 5.1 功能说明

用户创建一个服饰电商 AI 模特商品图审核批次，填写批次名称、品类、目标渠道和图位，并指定复核人。

当前初始品类默认值为女装上装和连衣裙；具体发布渠道/图位仍未冻结。

> **未验证假设 B-01：** 一个批次通常对应一个渠道、一个图位和一组统一规则。真实团队是否会在同一批次混合渠道，待访谈验证。

### 5.2 Given / When / Then 验收

**场景：创建合法批次**

- Given 用户拥有批次创建权限；
- And 已填写批次名称、场景、品类、渠道/图位状态和复核人；
- When 用户保存批次；
- Then 系统创建唯一 `batch_id`；
- And 状态为 `DRAFT`；
- And 记录创建人和时间；
- And 场景固定为 `fashion_ecommerce_ai_model_image`。

**场景：渠道或图位未知**

- Given 用户尚不能确认具体渠道或图位；
- When 用户创建批次；
- Then 系统允许保存为草稿；
- And 将渠道要求标记为 `NOT_VERIFIED` 或 `LIMITED`；
- And 在提交评估前提示该缺失可能导致 `REVIEW`；
- And 不得默认任何平台规范已经通过。

**场景：不支持的素材场景**

- Given 用户选择视频、纯商品白底图或其他未支持场景；
- When 用户尝试提交；
- Then 系统阻止进入当前工作流；
- And 明确提示该场景不在 MVP 范围；
- And 不得套用服饰电商 AI 模特图标准生成结论。

## 6. 输入契约与素材校验

### 6.1 候选图输入

每张候选图必须具有：

- 唯一 `asset_id`；
- 可计算的 SHA-256；
- 关联 SKU；
- 文件可读；
- 可识别的图片格式；
- 明确的场景值。

图片尺寸、格式上限和单批数量尚未基于真实流程验证。

> **未验证假设 I-01：** MVP 支持的格式、分辨率、文件大小和单批数量需要在技术基线与客户访谈后确定。

### 6.2 商品参考材料

建议包含：

- 商品正面、背面和关键细节参考图；
- SKU 基本信息；
- 不可改变项：颜色、结构、版型、印花、Logo、文字和数量；
- 参考材料的来源或授权状态。

### 6.3 可选业务材料

- 品牌规范；
- 渠道与图位要求；
- 地区、平台或法务规则；
- 原始生成参数或 Prompt；
- 历史审核备注。

原始 Prompt 不是评估结论的必要输入；缺失时输出模型无关的修改动作。

### 6.4 Given / When / Then 验收

**场景：完整输入通过校验**

- Given 候选图可读且具有唯一标识和哈希；
- And 已关联 SKU 和商品参考材料；
- When 用户提交批次；
- Then 系统记录候选图与参考材料的关联；
- And 进入 `VALIDATING`；
- And 校验成功后进入 `READY`；
- And 任何后续审核运行绑定此次输入快照。

**场景：候选图不可读**

- Given 图片损坏、格式无法解析或内容无法加载；
- When 执行输入校验；
- Then 模型层状态为 `UNREADABLE_ASSET` 或在模型调用前阻止运行；
- And 业务决策保持 `null`；
- And 批次进入 `INPUT_REQUIRED` 或 `EVALUATION_PARTIAL`；
- And 提示用户重新上传；
- And 不得把技术失败归类为图片质量 `REJECT`。

**场景：缺少商品参考图**

- Given 候选图可读；
- But 未提供足以核验商品事实的参考材料；
- When 输入校验完成；
- Then `scope.product_fidelity.status` 为 `NOT_VERIFIED` 或 `LIMITED`；
- And 系统不得声明商品忠实度通过；
- And 规则层输出 `REVIEW`，或在明确限定范围的模式下仅执行图内质量评估；
- And 人工检查项提示补充参考材料。

**场景：输入在运行后发生变化**

- Given 某候选图已产生审核运行；
- When 用户替换候选图、参考图、SKU 不可改变项或渠道规则；
- Then 系统保留原输入与原运行；
- And 创建新输入版本；
- And 原结论标记为已被新版本替代但不删除；
- And 必须重新运行后才能产生针对新输入的结论。

## 7. 可评估性检查

### 7.1 检查范围

在业务质量判断前检查：

- 候选图是否可读；
- 是否包含预期的模特与商品主体；
- 商品关键区域是否因裁切、遮挡或分辨率不足而不可判断；
- 候选图与参考材料是否属于同一 SKU；
- 必要的渠道、品牌或合规材料是否齐全；
- 是否存在输入冲突。

### 7.2 处理原则

- 可通过补材料解决：`REVIEW`；
- 候选图本身不可用于发布：可命中可评估性门禁并 `REJECT`；
- 技术系统无法运行：决策为 `null`；
- 不得把“没有发现问题”等同于“已完成核验”。

### 7.3 Given / When / Then 验收

**场景：关键商品区域被遮挡**

- Given 商品关键结构被姿态、裁切或其他物体遮挡；
- When 系统无法基于当前证据判断商品忠实度；
- Then 生成 `assessability` 类观察；
- And 状态为 `not_assessable` 或 `suspected`；
- And 结论至少为 `REVIEW`；
- And 列出需要补拍、补图或人工检查的具体区域。

**场景：输入 SKU 冲突**

- Given 候选图关联 SKU-A；
- But 商品参考图元数据显示 SKU-B；
- When 输入校验发现冲突；
- Then 停止该素材的业务评估；
- And 业务决策为 `null`；
- And 提示修正关联关系；
- And 审计记录保存冲突事实。

**场景：图像足以评估但品牌规范缺失**

- Given 候选图、商品参考和 SKU 信息完整；
- But 未提供品牌规范；
- When 运行审核；
- Then 商品与图内质量检查可以继续；
- And `scope.brand_guideline.status` 为 `NOT_VERIFIED`；
- And 不得声明品牌符合度通过；
- And 需要品牌确认的事项进入人工检查清单。

## 8. 系统评估与规则决策

### 8.1 模型观察层

模型观察层输出事实性观察，不输出发布结论。每条观察遵循当前契约：

- `observation_id`；
- `issue_code`；
- `category`；
- `severity`；
- `status`；
- `region`；
- `observation`；
- `impact`；
- `confidence`；
- `evidence_refs`。

### 8.2 Schema 校验

只有通过 `evaluation-result.schema.json` 或对应模型观察子契约校验的数据才能进入规则层。非法 issue code、缺失证据、越界坐标、非法严重度或未知字段均视为无效输出。

### 8.3 规则层

规则层依据版本化门禁生成：

- `PASS / REVIEW / REJECT`；
- 决策理由；
- 门禁命中；
- 软评分；
- 必要人工检查；
- 修改动作。

Blocker 直接触发 `REJECT`。Major/Minor 聚集、自动置信度和 `PASS` 阈值目前未标定。

> **未验证假设 E-01：** Blocker、Major、Minor 的现有严重度来自标准骨架，尚未通过真实业务多人标注确认。  
> **未验证假设 E-02：** 验证期不启用基于数量的 Major/Minor 自动升级规则，除非规则版本明确记录为实验配置。

### 8.4 Given / When / Then 验收

**场景：确认的 Blocker**

- Given 已验证观察中存在状态为 `detected` 的 Blocker；
- And 该观察满足当前门禁规则要求；
- When 规则引擎执行；
- Then 系统决策为 `REJECT`；
- And `gate_hits` 包含对应门禁和观察 ID；
- And 任何软评分都不得改变该结论；
- And 决策记录绑定 gates 版本。

**场景：疑似 Blocker**

- Given 存在严重问题迹象；
- But 观察状态为 `suspected` 或证据不足；
- When 规则引擎执行；
- Then 系统决策为 `REVIEW`；
- And 列出人工需确认的部位和问题；
- And 不得自动升级为 `PASS`。

**场景：模型输出不符合 Schema**

- Given 模型调用成功返回内容；
- But 内容未通过 Schema 校验；
- When 规则层尝试执行；
- Then 模型层状态为 `INVALID_OUTPUT`；
- And 规则层状态为 `INVALID_MODEL_OUTPUT` 或 `NOT_RUN`；
- And 业务决策为 `null`；
- And 保存可诊断但不含凭证的错误与原始响应引用。

**场景：验证期产生 PASS**

- Given 输入范围充分；
- And 无 Blocker；
- And 当前规则输出 `PASS`；
- When 结果进入批次列表；
- Then 素材必须进入 `AWAITING_HUMAN_REVIEW`；
- And 标记“验证期 PASS，尚未人工批准”；
- And 在人工复核前不得产生 `APPROVED_FOR_PUBLISHING_FLOW`。

## 9. 批次分流列表

### 9.1 列表目标

批次结果以三个业务分组呈现：

- `PASS`：验证期仍待人工复核；
- `REVIEW`：需要补材料、人工判断或局部返工；
- `REJECT`：存在阻断项，必须返工后复审。

技术失败和未运行素材单独显示，不混入三类业务结论。

### 9.2 最低展示字段

- 缩略图和素材版本；
- SKU；
- 系统决策；
- 人工复核状态；
- 首要决策理由；
- Blocker/Major/Minor 数量；
- 未验证范围；
- 运行状态；
- 返工状态；
- 最近更新时间。

排序和筛选至少应支持：

- 系统决策；
- 人工复核状态；
- 严重度；
- SKU；
- 未验证范围；
- 运行失败；
- 是否已有返工版本。

### 9.3 Given / When / Then 验收

**场景：正确分组**

- Given 批次内存在不同系统决策和技术状态；
- When 用户打开批次列表；
- Then `PASS`、`REVIEW`、`REJECT` 分组数量与最新有效运行一致；
- And 技术失败或决策为 `null` 的素材出现在独立异常区；
- And 人工改判不覆盖系统原始分组信息。

**场景：显示未验证范围**

- Given 某素材未核验商品忠实度或品牌规范；
- When 用户查看列表；
- Then 列表明确显示“商品未核验”或对应范围提示；
- And 不得仅显示绿色状态造成全部通过的误解。

**场景：验证期 PASS 待复核**

- Given 列表中存在系统 `PASS`；
- When 发布复核人筛选待处理项；
- Then 所有未人工确认的 `PASS` 均可被检出；
- And 批次不能在这些项未处理时标记为 `COMPLETED`。

## 10. 单图证据详情

### 10.1 页面目标

让人工能回答：

- 系统看到了什么；
- 在图片哪个区域；
- 为什么影响发布；
- 命中了哪条规则；
- 哪些范围没有核验；
- 应该如何处理。

### 10.2 最低展示内容

- 候选图与商品参考图并列查看；
- 可开关的问题区域标注；
- 系统决策、决策理由和门禁命中；
- 按严重度排列的观察；
- 每条观察的证据、影响和置信度；
- 软评分及“不可抵消门禁”说明；
- 未验证范围和必要人工检查；
- 模型无关的修改动作；
- 运行、输入和标准版本信息。

软评分不可用时显示“未评分/不可评估”，不得显示 0 分代替缺失。

### 10.3 Given / When / Then 验收

**场景：查看门禁证据**

- Given 某素材因 Logo 错误被 `REJECT`；
- When 用户打开单图详情；
- Then 页面定位 Logo 相关区域；
- And 展示观察事实、影响、严重度、置信度和证据引用；
- And 展示命中的 `text_logo` 门禁；
- And 明确说明软评分不能改变 `REJECT`。

**场景：无边界框的全图问题**

- Given 问题属于整体光影或缺少参考材料；
- When 用户查看证据；
- Then 页面支持 `FULL_IMAGE` 或无框证据表达；
- And 不得伪造精确坐标；
- And 仍展示证据来源和限制。

**场景：查看版本信息**

- Given 素材已有评估结果；
- When 审计查看者展开运行信息；
- Then 能查看 taxonomy、gates、Prompt、适配器、模型快照和配置版本；
- And 能关联到原始响应引用；
- And 不暴露 API 密钥或其他凭证。

## 11. 人工复核与改判

### 11.1 原则

- 验证期每个系统 `PASS` 必须人工处理；
- 人工确认或改判必须填写责任人和时间；
- 改判必须选择原因码并填写必要说明；
- 系统原始决策不可被覆盖；
- 改判数据可以进入后续标准评审，但不能自动修改生产门禁。

建议原因码：

```text
SYSTEM_FALSE_POSITIVE
SYSTEM_FALSE_NEGATIVE
INSUFFICIENT_REFERENCE
BUSINESS_CONTEXT_MISSING
BRAND_EXCEPTION
CHANNEL_EXCEPTION
COMPLIANCE_ESCALATION
STANDARD_DISAGREEMENT
OTHER
```

### 11.2 Given / When / Then 验收

**场景：人工确认 PASS**

- Given 系统决策为 `PASS`；
- And 当前处于验证期；
- When 发布复核人完成证据检查并确认；
- Then 保存 `CONFIRM_PASS`、复核人和时间；
- And 最终处置可变为 `APPROVED_FOR_PUBLISHING_FLOW`；
- And 审计中同时保留系统与人工结论。

**场景：将 PASS 改为 REJECT**

- Given 系统决策为 `PASS`；
- When 复核人发现阻断问题并改判；
- Then 必须选择原因码；
- And 对 `OTHER` 必须填写说明；
- And 保存改判后的严重问题和必要证据；
- And 最终处置为 `REJECTED` 或 `REQUIRES_ACTION`；
- And 该记录进入误放风险评测数据。

**场景：将 REJECT 改为 PASS**

- Given 系统决策为 `REJECT`；
- When 复核人认为门禁不适用并改判；
- Then 必须填写规则不适用原因和业务证据；
- And 记录复核人、时间及使用的标准版本；
- And 不得删除原门禁命中；
- And 该记录进入标准分歧队列。

**场景：无权限用户尝试改判**

- Given 用户不具备发布复核权限；
- When 用户尝试确认或修改业务结论；
- Then 系统拒绝操作；
- And 不改变任何结论；
- And 可记录被拒绝的操作事件。

## 12. 返工与复审

### 12.1 返工原则

- 返工图是新素材版本；
- 新版本关联原版本和要解决的问题；
- 不覆盖原图片、原运行或人工结论；
- 复审使用当时有效且明确记录的标准版本；
- 若标准版本发生变化，结果中必须显示版本差异，避免把标准变化误认为图片改善。

### 12.2 返工任务

返工任务至少包含：

- 来源素材及版本；
- 触发返工的观察 ID；
- 必须修复项；
- 必须保持不变项；
- 可选建议；
- 责任人和目标状态；
- 新版本关联。

### 12.3 Given / When / Then 验收

**场景：提交返工版本**

- Given 某素材最终处置为 `REQUIRES_ACTION` 或 `REJECTED`；
- When 创建者上传修复后的图片；
- Then 创建新的 `asset_id` 或 `asset_version`；
- And 设置 `parent_asset_id`；
- And 原版本保留且标记已存在后继版本；
- And 新版本必须重新经过输入校验和完整审核。

**场景：验证问题是否修复**

- Given 新版本完成评估；
- When 用户查看版本对比；
- Then 能看到原观察、原证据和新版本对应结果；
- And 每个必须修复项标记为“已解决、仍存在、无法判断或出现新问题”；
- And 不因原问题消失而忽略新出现的 Blocker。

**场景：标准版本变化**

- Given 原版本使用 gates v0.1；
- And 新版本审核时使用不同 gates 版本；
- When 用户比较前后结果；
- Then 页面显示两次运行的标准版本；
- And 明确提示结论变化可能同时来自图片和规则变化；
- And 不自动计算纯图片改善率，除非使用同一冻结配置重跑。

## 13. 审计与追溯

### 13.1 必须记录的事件

- 批次创建、编辑、提交和取消；
- 素材上传、替换和版本创建；
- 参考材料及适用范围变化；
- 每次模型调用与规则执行；
- Schema 或技术失败；
- 系统决策产生；
- 人工查看、确认、改判及原因；
- 返工任务创建与复审；
- 标准版本发布；
- 导出和数据删除申请。

### 13.2 审计记录字段

```text
event_id
event_type
actor_id
actor_role
batch_id
asset_id
run_id
before_ref
after_ref
reason_code
reason_text
created_at
```

审计记录原则上追加写入。需要纠错时创建更正事件，不原地篡改历史。

### 13.3 Given / When / Then 验收

**场景：追溯一次改判**

- Given 某素材系统 `PASS` 被人工改为 `REJECT`；
- When 审计查看者查询该素材；
- Then 能看到原系统结果、门禁版本、改判人、时间、原因和最终处置；
- And 能关联对应输入与运行；
- And 历史记录顺序完整。

**场景：重跑同一素材**

- Given 同一输入以不同模型快照或 Prompt 版本重跑；
- When 查看审计记录；
- Then 每次运行拥有独立 `run_id`；
- And 显示各自配置、结果、延迟和成本状态；
- And 任一次结果都未被静默覆盖。

**场景：技术失败**

- Given 某次模型调用超时；
- When 系统记录该事件；
- Then 保存 `TIMEOUT`、尝试次数和必要错误信息；
- And 决策为 `null`；
- And 后续重试创建新运行记录；
- And 不将超时记录成业务 `REVIEW`。

## 14. 批次完成条件

一个验证期批次只有同时满足以下条件才能为 `COMPLETED`：

- 每张可处理素材都有有效系统结果或明确的失败处置；
- 所有系统 `PASS` 已完成 100% 人工复核；
- 所有 `REVIEW` 已被人工确认、补材料、退回或创建返工任务；
- 所有 `REJECT` 已被确认或有改判记录；
- 没有未处理的权限、输入或技术异常；
- 审计记录完整。

### Given / When / Then 验收

**场景：存在未复核 PASS**

- Given 批次中至少一个系统 `PASS` 尚未人工复核；
- When 用户尝试完成批次；
- Then 系统拒绝将状态改为 `COMPLETED`；
- And 显示未处理素材数量和入口。

**场景：所有项均已处置**

- Given 所有素材满足完成条件；
- When 发布复核人完成批次；
- Then 状态变为 `COMPLETED`；
- And 记录完成者和时间；
- And 批次摘要分别统计系统决策、人工结论、改判和失败；
- And 不把人工批准数量表述为自动发布数量。

## 15. 未来 MVP 的非功能要求

以下要求需要技术基线后补充数值：

- 可复现：冻结输入和配置时，规则层结果应确定；
- 可追溯：每个结论可追到输入、观察、门禁和版本；
- 安全：原始响应和日志不得包含凭证；
- 隐私：客户素材的保存、访问、导出和删除策略必须在真实试点前确定；
- 失败安全：技术失败不得生成虚假业务通过；
- 可访问性：问题不能只靠颜色表达；
- 性能：单图延迟、批次并发和成本上限待离线基线测量；
- 数据完整性：历史运行、改判和返工版本不得被静默覆盖。

> **未验证假设 N-01：** 客户可接受的单批规模、等待时间、单图成本和图片留存期限尚不明确。  
> **未验证假设 N-02：** 是否需要私有化、区域化存储或禁止第三方模型处理，必须在接触真实素材前确认。

## 16. 产品评测指标

产品化后至少跟踪：

- 系统与人工三分类一致性；
- Blocker 召回率和误报率；
- 系统 `PASS` 被人工改为返工或拒绝的比例；
- 系统 `REJECT` 被人工改为通过的比例；
- `REVIEW` 占比和人工承接量；
- 单批人工审核耗时变化；
- 返工后问题解决率；
- 模型多次运行稳定性；
- 技术失败率与 Schema 通过率；
- 每张图的延迟和成本。

当前不设置虚构的 Go 阈值。阈值由真实业务损失、人工承接能力和盲测结果共同确定。

本 PRD 进入开发前必须满足：
