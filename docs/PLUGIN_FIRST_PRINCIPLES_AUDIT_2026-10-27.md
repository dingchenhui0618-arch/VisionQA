# VisionQA 插件第一性原理审计

日期：2026-10-27  
范围：仅审计插件能力、交互效果和非技术用户可用性；不评价市场规模、客户采用或商业回报。

## 结论先行

VisionQA 当前不应该继续堆 Provider、模型、版本树或更多评审维度。下一阶段的主要工作应是收敛 UI 和统一运行语义，把插件变成一个普通人能够理解的“看一眼、说一句、得到可执行判断”的工具。

当前存在两个必须先解决的能力断点：

1. Chrome/MCP v0.2 Host route 的真实 Provider 分支仍通过 v0.1 兼容桥，DOM evidence anchors 和 revision 没有进入结构化结果；Mock 能看到 v0.2，真实路径却没有同等证据链。
2. Chrome popup 固定调用 `provider: mock` 和 `localhost:6300`，结果只是原始 JSON；网页 `/plugin` 手动上传走另一套 v0.1 Mock 语义。同一份视觉证据从不同入口进入，会得到不同的决策表达。

这不是功能数量问题，而是产品的核心承诺尚未收敛为一条稳定路径。

## 第一性原理：插件究竟要替用户完成什么

把所有模型、Provider、契约和桌面壳暂时拿掉，只保留用户真正需要的五步：

1. **拿到同一份视觉证据**：当前页面截图或用户拖入的产物图。
2. **理解这次要判断什么**：默认检查目标，必要时用一句自然语言补充。
3. **定位影响最大的地方**：指出“哪里”以及截图/DOM 中的证据，而不是先给分数。
4. **给出下一步**：用普通人能执行的语言说明改什么、为什么改、改完如何确认。
5. **复验同一对象的新版本**：重新采集后确认 revision 已变化，并说明问题是否仍存在。

因此产品价值不是“调用了哪个模型”，而是减少用户从视觉问题到可执行决定之间的认知距离。

## 当前能力审计

### 已经具备的部分

- Host adapter 能采集截图、页面标题、DOM 文本、标题层级、交互摘要、元素几何、有限 computed style、选中元素和 revision。
- VisualReview、CodeReview、Linked 三类契约与离线 Mock 流程已经存在。
- Provider 有本地密钥边界，默认失败关闭，不把 Key 放进 Renderer 或公开仓库。
- 评审结果保留人工确认边界，不自动写回宿主源码。
- 当前插件界面已有证据缩略图、结果、上下文、版本和桌面 Provider 设置入口。

### P0：必须先修的能力一致性

#### [P0] v0.2 证据没有完整进入真实 Provider 结果

- 位置：`web/app/api/visual-review/host/route.ts`
- 现状：v0.2 Host capture 在 Mock 分支使用 v0.2 request；真实分支调用 `hostEvidenceToLegacyVisualReviewRequest`，最终返回 v0.1 结果。
- 影响：模型虽然收到截图和文字摘要，但结果结构里无法稳定表达 DOM 锚点、选中元素和 revision；“指出页面哪里有问题”无法闭环。
- 方向：先统一内部结果适配器，让 v0.2 证据成为真实和 Mock 的共同输入；旧 v0.1 仅作为开发者兼容层。

#### [P0] 两个入口产生两种不同结果语义

- 位置：`web/host/chrome/popup.js`、`web/app/plugin/plugin-workspace.tsx`、两条 API route。
- 现状：Chrome popup 固定请求 Mock，网页插件手动上传走 v0.1 Mock；二者对“不可评估/需要人工判断”的表达不同。
- 影响：普通用户无法知道哪个结果才是可信的，也无法把一次 Host 评审继续带入主插件界面。
- 方向：定义一个 UI-facing review result adapter；入口可以不同，但必须共享同一决策枚举、证据展示和下一步动作。

### P1：非技术用户的主要认知负担

- 首屏使用“产物图、视觉证据、验收重点、宿主上下文”等内部术语，没有告诉用户“把当前页面交给我检查什么”。
- 真正重要的目标、场景和保留约束隐藏在“上下文”页；默认值会让用户误以为上下文已经完整。
- 结果默认显示 Provider/model、严重度、置信度百分比和原始 category，这些是审计细节，不是普通用户的第一决策信息。
- “版本”页直接展示 JSON contract，不能帮助用户采取下一步行动。
- Provider ID、Endpoint、模型、Key 和请求上限在普通插件界面里过于突出，应归入桌面端“高级连接设置”。
- Chrome popup 的 `<pre>` JSON 结果不适合非技术用户，也没有把证据缩略图或可点击锚点带回主界面。

### P2：已有能力没有被 UI 消费

- Host evidence 的 DOM selector、rect、computed style 和 revision 已在契约中存在，但默认结果只呈现文本，不呈现“问题发生在哪个区域”。
- Profile registry 已有 visual/code/linked 语义，但普通用户看不到通俗的任务选择或自动选择解释。
- `requires_approval=true` 已在契约里表达，UI 还缺少明确的“接受建议 / 重新采集 / 查看证据”动作。

## 与现存插件的效果对照

这里比较的是交互结果和用户感受，不是市场排名：

| 工具 | 用户第一动作 | 反馈形式 | 对 VisionQA 的启发 | VisionQA 当前差距 |
| --- | --- | --- | --- | --- |
| [VisBug](https://chromewebstore.google.com/detail/visbug/cdockenadnadldjbbgcallicgledbeoc) | 直接点页面元素 | 立即出现元素、间距、样式和层级反馈，可继续修改 | 视觉工具要让用户直接指向页面，而不是先理解开发概念 | VisionQA 能采集元素，但没有把结果锚定回页面并让用户继续操作 |
| [Chrome Lighthouse](https://developer.chrome.com/docs/devtools/lighthouse) | 选择审计类别后运行 | 高层结论 + 具体问题 + 建议，适合非专家快速读报告 | 先给“现在该做什么”，细节放后面 | VisionQA 当前把模型、置信度和 JSON 放得太前 |
| [Stark](https://www.getstark.co/release-notes/) | 选择对象或运行某类检查 | 按问题分组、可过滤、可定位，逐项给出修正方向 | 证据和动作必须紧邻，避免一长串散乱报告 | VisionQA 已有 issue/evidence 字段，但默认 UI 尚未形成可定位清单 |

这些工具的共同点不是功能最多，而是：

- 第一动作明确；
- 结果优先于配置；
- 问题、证据和下一步在同一个阅读路径里；
- 专业细节可展开，但不会阻塞第一次使用。

## 决策：优先调整 UI，但先修两个 P0

不建议继续增加以下内容：

- 更多 Provider 或模型选择；
- 更复杂的评分体系；
- 版本树、自动修图或源码写回；
- 更多 Code/Linked/电商 profile 的入口。

这些能力可以保留在 runtime 和开发者详情中，但现在增加入口只会扩大普通用户的选择成本。

下一阶段顺序固定为：

1. **统一结果语义**：真实/MOCK/Chrome/网页入口使用同一 UI-facing result adapter。
2. **默认入口收敛**：优先“评审当前页面”；手动上传作为第二入口，不再要求用户先理解上下文概念。
3. **证据优先结果**：默认显示截图缩略图、问题区域/元素、为什么、下一步；模型名、置信度、原始 Contract 放进详情。
4. **复验动作明确**：提供“重新采集当前页面”和 revision 对比；不自动写回源码。
5. **高级设置后置**：Provider、Key、Endpoint、模型只在桌面端高级设置可见。
6. **最后才做视觉 polish**：修正窄屏溢出、按钮层级、空白比例、焦点态和状态文案。

## 非技术用户验收标准

每完成一项都必须重新问自己：

> 一个没有代码基础的人，只看当前界面，能否在 30 秒内完成一次评审，并知道结果是否可信、问题在哪里、下一步做什么？

具体必须同时满足：

- 首屏只有一个主动作：“评审当前页面”或“添加要评审的图片”；
- 不要求用户理解 DOM、revision、Provider、Contract、endpoint、置信度；
- 没有证据时明确说明“还缺什么”，不显示假结论；
- 结果最多先展示三个优先问题，每个问题都带“位置 / 原因 / 下一步”；
- 结果页有“重新采集并复验”动作；
- 真实调用失败时说明“没有形成判断、没有修改文件、下一步怎么做”；
- 键盘、窄屏和触控都能完成同一条主路径。

## 当前阶段判断

当前插件的契约和运行时基础已经足以支撑第一版视觉评审，但产品表达还没有达到“人人可用”。下一步不是扩展能力面，而是把已有能力压缩成一条没有术语、没有分叉、证据可追踪的主路径。

本文件完成的是审计和路线冻结，不把 Mock 结果、工程测试或已有 UI 误称为真实模型质量证明。

## 本轮落地与自检（2026-10-27）

### 已完成：v0.2 结果边界收敛

- Host 真实 Provider 仍复用既有 v0.1 Provider 请求，但现在通过明确的适配器回到 v0.2 响应；不再把这条路径直接当成 v0.1 结果交给 Host 消费者。
- `revision_id` 进入 v0.2 响应；请求中的 DOM selector/rect 会作为 `evidence_anchors` 保留，旧 Provider 的文字证据会被标为文本锚点，避免证据在兼容层静默丢失。
- 增加了回归测试，确认 revision、DOM anchor 和人工批准边界都保留；`npm run test:plugin` 当前 35/35 通过。

自问：**同一份 Host 证据是否能在结果中回溯到 revision 和页面元素？**

答案：**结构化链路已达到；元素级“点击后高亮页面”仍未完成，下一阶段必须继续做，不把字段存在误称为交互闭环。**

### 已完成：首屏语言和窄屏可用性收敛

- 空态和主动作从“产物图 / 验收重点 / 视觉证据”收敛为“作品 / 这次想重点看什么 / 开始检查”，降低非技术用户的术语负担。
- 修复插件页面在 320px 视口下因共享页面的 `min-width: 320px` 导致的横向滚动；实际 IAB 检查结果为 `body.scrollWidth === 319`、`document.documentElement.scrollWidth === 319`、`clientWidth === 319`，无横向溢出。
- `npm run build` 通过；本轮全量 lint 无报错。上述证据仍是工程/布局证据，不代表真实 Provider 质量或用户完成率。

自问：**没有代码基础的人只看空态，能否知道先放什么、要做什么？**

答案：**比上一版清楚，但还不能称为完成。当前仍需把“评审当前页面”作为第一入口、把结果改成证据优先，并补上重新采集/复验动作。**

### 进行中：结果页证据优先

- 结果页现在会把本次作品缩略图放在结论前，问题最多先显示三项，并把类别、严重度和置信度改写成普通人可读的“哪里 / 下一步 / 优先级”。
- Provider/model 不再出现在首个结果标题里；高级运行信息仍保留在设置与版本页，避免第一次阅读被实现细节打断。
- 增加“用当前作品再次检查”和“查看检查记录”两个明确动作。前者只代表重新发送当前文件，尚未宣称宿主 revision 已变化；revision 复验仍是下一项工作。

自问：**用户看到结果后，是否能先看到自己交给插件的东西，并知道下一步？**

答案：**首屏阅读路径已达到；当前还不能称为完整闭环，因为手动上传与 Chrome Host 尚未共享同一个 UI-facing 结果对象，问题也还没有反向高亮到宿主页面。**

### 进行中：宿主容器改为持续侧边面板

- Chrome 扩展增加 Side Panel 配置和最小 Service Worker：点击扩展动作时，优先打开可持续停留在页面旁的评审面板，而不是一次性弹出 JSON 工具。
- Popup/Side Panel 共用同一份页面截图、DOM 摘要、对话上下文和结果渲染；本地服务 6300 不可用时，会按 6301 备用端口尝试，扩展权限也同步覆盖两个本地端口。
- 这一步不增加模型能力，只改变证据采集和结果阅读的容器。Chrome 官方将 Side Panel 定位为“与网页主内容并行、持续伴随浏览过程”的体验，适合 VisionQA 的复验循环（[Side Panel API](https://developer.chrome.com/docs/extensions/reference/api/sidePanel)）。

自问：**用户能否在页面旁持续看到“当前页面—结果—下一步”，而不必反复打开一次性工具？**

答案：**结构上已达到；真实浏览器扩展需要重新加载 manifest 后再做一次点击验收，当前本地页面尚未把宿主结果自动回填到 `/plugin` 主界面。**

### 已完成：统一 UI-facing 结果适配器

- 新增 `web/lib/visionqa/review-ui-adapter.ts`，把 v0.1 与 v0.2 结果统一为 `visionqa-ui-v0.1`。
- 网页上传 API 和 Chrome Host API 都返回同一份 `ui_result`；首层只表达结论、最多三项问题、证据、下一步和复验检查。
- Provider、模型、置信度、原始 Contract 仍保留在底层响应或高级页面，但不再决定普通用户第一眼看到的语言。
- 新增两条适配器测试，并把 Host route 断言扩展到 `ui_result`；`npm run test:plugin` 当前 37/37 通过。

自问：**同一份证据从网页入口或 Host 入口进入，普通用户是否会看到同一种结果语言？**

答案：**适配器层已经达到；页面定位和 revision 变化仍未达到，因此暂不结束目标。**

另外，桌面 Provider 状态现在只有在一次非计费的配置检查确认服务可达且就绪后才显示“可用”；没有检查证据时显示“待检查”，避免把“配置文件存在”误导成“已经可以完成判断”。

### 下一项停止条件

在以下三点完成并通过本文件的自问前，不继续堆 Provider、模型或额外 Profile：

1. Chrome/MCP Host 与网页上传使用同一份 UI-facing v0.2 结果适配器；
2. 结果页默认显示真实证据缩略图、最多三个问题的定位和下一步；
3. 用户可以从当前结果一键重新采集并看到 revision 是否变化。
